## 성능 측정

모바일 390×844, DPR 2, CPU 20배 감속, 대역폭 400kbps·지연 400ms로 원본 측정
도구를 사용합니다. 서버를 예열하고 매번 새 브라우저 프로필을 사용하며 HTTP
캐시·서비스 워커·GA를 제외합니다. 페이지 로드·폰트·네트워크 안정화 후 5초까지
관찰합니다. 동일한 Windows 호스트와 Node 24.20.0의 프로덕션 빌드를 비교합니다.
환경에서 실행 가능한 Playwright Chromium Headless Shell을 모든 버전에 똑같이
사용합니다. 실사용자의 Core Web Vitals나 INP 수치로 해석하지 않습니다.

원본 참조본에는 같은 개인 글·프로필·생성 자산과 로컬 실행에 필요한 경로 및
빈 영문 목록 처리를 적용했습니다. 일반 화면·공유 패키지는 고정한 원본입니다.
복원 전 버전에는 Windows 경로 호환 수정만 적용했습니다.

복원 전 홈은 `/en` 미리 불러오기 요청이 404를 반환해 원본 도구의 엄격한 자원
검사를 통과하지 못했습니다. 해당 측정은 유효한 기준값으로 집계하지 않습니다.
실패 요청과 trace는 `.cache/performance/legacy`에 보존합니다.

원본 참조본 대비 각 경로·버전 5회씩, 총 20회 측정했습니다. 단위는 ms이며
표의 편차는 5회 값의 모집단 표준편차입니다. LCP 대상은 두 버전에서 같았습니다.

| 경로·버전      | LCP 중앙값 ± 편차 | LCP 최소~최대 | CLS 중앙값 | 긴 작업 총시간 중앙값 | 초기 JS / CSS 전송량 |
| -------------- | ----------------- | ------------- | ---------- | --------------------- | -------------------- |
| 홈·원본 참조   | 3,488 ± 343       | 3,156~4,200   | 0.0696     | 1,096                 | 187,992 / 26,070 B   |
| 홈·복원본      | 3,396 ± 341       | 3,184~4,072   | 0.0696     | 691                   | 187,937 / 26,070 B   |
| 본문·원본 참조 | 3,620 ± 296       | 3,032~3,872   | 0          | 1,109                 | 197,424 / 33,001 B   |
| 본문·복원본    | 3,368 ± 314       | 3,208~4,112   | 0          | 816                   | 197,361 / 33,001 B   |

본문 경로는 `/2026/09/blog-java-functional-interface-lambda`입니다. 원본 참조
대비 LCP 중앙값 변화는 홈 -2.64%, 본문 -6.96%입니다. JS는 각각 -0.03%,
CSS는 같습니다. 측정한 두 경로 모두 LCP·JS·CSS 10% 악화 기준을 통과했습니다.
차이는 측정 편차 안에 있어 성능 향상으로 일반화하지 않습니다.

개별 시행 값과 모든 지표의 최소·최대·표준편차, 실행 환경·빌드 식별자는
[성능 원자료](restoration-performance.json)에 기록했습니다. 압축 trace와 전체
요청 목록은 로컬 `.cache/performance/reference`에 있습니다. 긴 작업 총시간은
각 시행의 관찰 구간 기준이며 Lighthouse TBT와 다릅니다. 원본 도구의
`loadBlockingMs`도 원자료에 별도로 보존했습니다.
측정 후 과거 별칭의 대상만 수정해 다시 빌드했고, 측정한 두 경로의 초기
JS·CSS 파일 해시 경로가 측정본과 일치하는지 확인했습니다.

## 운영과 적용

Docker Compose 설정 검증은 통과했습니다. 수집 서비스 이름·허용 출처·대시보드와
개인 도메인, 기본값이 빈 분석 환경값을 확인했습니다. 분석·수집·푸시를 본인
계정에 연결하지 않았으므로 실제 이벤트·알림 수신·Grafana 도착은 미검증입니다.

동기화 로직은 변경 없음·정상 병합·개인 데이터 보호·충돌 보존·삭제·이름 변경·
반복 실행·이력 되돌림을 로컬 저장소로 검사했습니다. 하루 한 번의 workflow와
단일 브랜치·PR 생성 코드는 준비했지만 App 토큰을 이용한 실제 첫 PR은 미검증입니다.
운영 배포와 푸시 발송 workflow는 명시적인 활성화 변수 전에는 실행하지 않습니다.

남은 적용 순서는 [운영 문서](operations.md)에 따라 Vercel Preview를 검증하고,
본인 계정·기존 서버를 연결한 뒤 도메인을 전환하고 첫 동기화 PR을 확인하는 것입니다.
원격 push·배포·도메인 변경은 아직 수행하지 않았습니다.
