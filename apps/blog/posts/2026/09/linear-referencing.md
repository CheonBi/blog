# 센서가 "1,300m"라고만 말할 때, 지도에 점을 찍는 법

선형 센서는 위치를 위도와 경도로 보내지 않습니다. 기준점에서 얼마나 떨어져 있는지만 알려줍니다.

```json
{
  "sourceId": "sensor-01",
  "distanceM": 1300.0,
  "value": 0.42,
  "eventTime": "2026-09-01T10:15:30+09:00"
}
```

이벤트에는 distanceM이 있지만 지도에는 좌표가 필요합니다. 이 글은 누적거리를 지도 좌표로 바꾸는 선형참조(Linear Referencing) 모델을 설명합니다.

문제는 위도와 경도를 계산하는 데서 끝나지 않습니다.

- 이벤트 원본과 계산 결과를 분리해야 한다.
- 거리와 좌표의 출처가 다른 기준점을 표현해야 한다.
- 경로의 굴곡을 좌표에 반영해야 한다.
- 여러 이벤트를 처리할 때 질의 수를 줄여야 한다.
- 기준정보가 바뀌어도 이전 이벤트를 다시 계산할 수 있어야 한다.

이 글의 시설명, 좌표, 식별자와 수치는 이해를 돕기 위한 예시입니다. 특정 조직이나 장소를 설명하지 않고, 여러 선형 데이터 문제에 적용할 수 있는 구조와 계산식에 집중합니다.

## 1. 문제: 센서는 2차원을 모른다

센서가 선형 경로를 따라 발생한 이벤트를 다음처럼 보낸다고 하겠습니다.

```text
기준점에서 1,300m 떨어진 위치에서 이벤트 발생
```

이 값은 센서 관점에서는 충분합니다. 하지만 지도 화면에서는 다음 정보가 필요합니다.

```text
위도: ?
경도: ?
주변 설명: ?
```

센서가 보내는 거리를 지도 좌표로 바꾸는 과정을 선형참조라고 합니다. 도로의 기준점에서 몇 km 떨어진 위치를 찾거나, 선형 자산의 시작점에서 떨어진 위치를 지도에 표시할 때 같은 모델을 사용할 수 있습니다.

핵심은 거리축과 지도상의 경로를 연결하는 것입니다.

```text
거리축
0m ───── 500m ───── 1,000m ───── 1,500m
│         │           │             │
지도상의 기준점과 경로 좌표를 연결
```

기준점이 충분하면 이벤트 거리 양옆의 좌표를 찾을 수 있습니다. 그 두 좌표 사이에서 이벤트가 어느 정도 진행됐는지 계산하면 이벤트 좌표를 얻을 수 있습니다.

## 2. 설계 판단: 이벤트에 좌표를 저장하지 않는 이유

가장 단순한 구현은 이벤트가 들어오는 순간 좌표를 계산해 함께 저장하는 방식입니다.

```java
public long createEvent(EventRequest request) {
    GeoPoint point = resolver.resolve(request.routeId(), request.distanceM());

    return eventRepository.insert(
        request,
        point.latitude(),
        point.longitude()
    );
}
```

이 방식은 조회가 빠릅니다. 하지만 좌표는 이벤트가 직접 측정한 값이 아니라 기준정보에서 계산한 파생값입니다.

기준점의 좌표를 고치거나 경로에 굴곡점을 추가하면 같은 이벤트의 좌표도 달라질 수 있습니다. 이벤트 저장 시점의 좌표를 고정하면 기준정보를 개선해도 기존 이벤트에는 새 결과가 반영되지 않습니다.

그래서 원본과 파생값을 분리합니다.

```java
public record SensorEvent(
    long id,
    String routeId,
    double distanceM,
    double value,
    Instant eventTime
) {}
```

이벤트에는 센서가 보낸 값만 저장하고, 좌표는 조회 시점에 계산합니다.

```text
이벤트 저장
  └─ routeId, distanceM, value, eventTime

이벤트 조회
  └─ 최신 기준점 조회
  └─ distanceM으로 좌표 계산
  └─ 지도 응답에 latitude, longitude 추가
```

이 구조에는 다음 장점이 있습니다.

- 기준정보를 수정하면 과거 이벤트에도 최신 결과가 반영된다.
- 이벤트 테이블에 파생 좌표를 중복 저장하지 않는다.
- 실시간 알림은 새 이벤트가 생겼다는 신호만 보내도 된다.
- 좌표 계산 로직을 여러 화면이 따로 구현하지 않아도 된다.

센서가 준 거리는 원본이고 좌표는 기준정보를 이용한 해석입니다. 해석은 기준정보가 바뀔 때 다시 계산할 수 있어야 합니다.

## 3. 데이터 모델: 거리와 좌표의 출처를 분리한다

거리와 좌표의 대응표를 저장하는 테이블을 생각해 봅시다.

```sql
CREATE TABLE route_reference_point (
    id                    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    route_id              varchar(100) NOT NULL,
    distance_m            double precision NOT NULL,
    latitude              double precision,
    longitude             double precision,
    description           varchar(200),
    reference_kind        varchar(30) NOT NULL,
    distance_source       varchar(30) NOT NULL,
    coordinate_source     varchar(30) NOT NULL,
    created_at            timestamp NOT NULL,
    updated_at            timestamp NOT NULL
);
```

실제 서비스에서는 이름과 컬럼이 달라도 됩니다. 중요한 것은 한 행이 어떤 목적으로 만들어졌고, 거리와 좌표를 어디에서 얻었는지 구분하는 일입니다.

### 3.1 기준점과 경로점

경로에 사용하는 점은 두 종류로 나눌 수 있습니다.

| 종류           | 사람이 확정하는 값 | 시스템이 계산하는 값 | 역할                 |
| -------------- | ------------------ | -------------------- | -------------------- |
| 기준점(anchor) | 거리와 좌표        | 없음                 | 거리축의 눈금을 고정 |
| 경로점(vertex) | 좌표               | 거리                 | 지도상의 굴곡을 표현 |

기준점은 distanceM과 좌표를 함께 알고 있는 점입니다. 경로점은 지도에서 좌표를 지정했지만 거리축상의 위치는 아직 모르는 점입니다.

경로점의 거리를 반드시 사람이 측정해야 하는 것은 아닙니다. 양쪽 기준점 사이의 경로 길이 비율로 계산할 수 있습니다. 이렇게 하면 지도에서 굴곡을 추가하는 작업과 거리 측정 작업을 분리할 수 있습니다.

### 3.2 값의 출처를 하나의 상태로 합치지 않는 이유

한 점에서 거리와 좌표의 출처가 다를 수 있습니다.

| 거리 출처 | 좌표 출처   | 의미                                               |
| --------- | ----------- | -------------------------------------------------- |
| 측정값    | 지도 입력값 | 거리축은 신뢰할 수 있지만 좌표는 근사값일 수 있다. |
| 계산값    | 측정값      | 좌표는 확실하지만 거리는 기준점으로부터 계산했다.  |
| 측정값    | 측정값      | 거리와 좌표를 각각 확인했다.                       |

따라서 distance_source와 coordinate_source를 분리합니다. is_verified 같은 boolean 하나로 모든 신뢰도를 표현하면 어느 값이 검증됐는지 알 수 없습니다.

### 3.3 지도 데이터의 접근 경계

좌표와 주소가 민감한 데이터라면 애플리케이션의 일반 데이터와 보관·권한 범위를 분리할 수 있습니다.

```text
일반 이벤트 데이터
  └─ 센서 값과 시간

위치 기준 데이터
  └─ 좌표, 주소, 경로 형상
```

데이터베이스에서는 별도 스키마나 별도 저장소를 사용하고, 권한·백업·내보내기 정책을 분리할 수 있습니다. 보안 경계를 코드의 주석으로만 남기지 않고 저장 구조에 표현하면 운영 실수를 줄일 수 있습니다.

## 4. 핵심 연산: 선형보간

이벤트 거리 D를 감싸는 두 좌표점 P, Q를 찾았다고 하겠습니다.

```text
P.distance = 1,000m
Q.distance = 1,600m
D.distance = 1,300m
```

이벤트는 P에서 Q까지 절반 진행한 위치입니다.

```text
ratio = (D - P.distance) / (Q.distance - P.distance)

latitude  = P.latitude  + (Q.latitude  - P.latitude)  × ratio
longitude = P.longitude + (Q.longitude - P.longitude) × ratio
```

Java로 표현하면 다음과 같습니다.

```java
public record GeoPoint(double latitude, double longitude) {}

public record ReferencePoint(
    double distanceM,
    Double latitude,
    Double longitude
) {}

public static GeoPoint interpolate(
    ReferencePoint previous,
    ReferencePoint next,
    double distanceM
) {
    if (previous.latitude() == null || previous.longitude() == null
        || next.latitude() == null || next.longitude() == null) {
        return null;
    }

    double span = next.distanceM() - previous.distanceM();
    if (span < 0) {
        return null;
    }
    if (span == 0) {
        return new GeoPoint(previous.latitude(), previous.longitude());
    }

    double ratio = (distanceM - previous.distanceM()) / span;
    return new GeoPoint(
        previous.latitude()
            + (next.latitude() - previous.latitude()) * ratio,
        previous.longitude()
            + (next.longitude() - previous.longitude()) * ratio
    );
}
```

### 4.1 입력 범위를 확인해야 하는 이유

ratio는 일반적으로 0과 1 사이여야 합니다.

```text
ratio = 0    → previous 위치
ratio = 0.5  → 두 점의 중간
ratio = 1    → next 위치
```

ratio가 이 범위를 벗어나면 이벤트가 두 기준점의 바깥에 있다는 뜻입니다. 이런 값을 무조건 외삽하면 기준정보가 없는 구간을 추정하게 됩니다.

서비스의 정책에 따라 두 가지 방법 중 하나를 선택할 수 있습니다.

- 바깥 구간은 좌표를 만들지 않고 null로 반환한다.
- 데이터가 충분히 신뢰할 수 있을 때만 외삽하고 결과에 경고 상태를 붙인다.

기준이 없는 값을 정상 좌표처럼 저장하지 않는 것이 중요합니다.

### 4.2 위경도를 평면처럼 보간해도 되는가

위도와 경도는 구면 좌표지만, 짧은 구간의 위치를 보간할 때는 평면 보간을 실용적으로 사용할 수 있습니다. 이때 실제 오차는 지구 곡률보다 지도 좌표의 품질과 경로 형상에서 더 크게 발생하는 경우가 많습니다.

다만 보간과 거리 계산은 구분해야 합니다.

- 보간은 두 점 사이의 비율을 좌표에 적용한다.
- 거리 계산은 실제 길이를 구하므로 위도에 따른 경도 축척 차이를 반영해야 한다.

경로가 직선이면 기준점 간격이 넓어도 보간 오차가 작습니다. 반대로 기준점 사이에 큰 굴곡이 있으면 두 끝점을 직선으로 연결하는 것만으로 큰 오차가 생깁니다.

```text
기준점 ───────────── 기준점
          실제 경로는 굴곡

두 끝점만 사용하면 실제 경로와 지도상의 직선이 달라진다.
```

따라서 기준점을 일정한 간격으로 추가하기보다 경로가 바뀌는 지점에 추가하는 편이 효율적입니다.

## 5. 굴곡점의 거리를 경로 비율로 계산하기

경로점은 좌표를 알고 있지만 거리값을 모를 수 있습니다. 이 값을 양쪽 기준점의 거리 사이에 배분합니다.

### 5.1 Haversine으로 두 좌표 사이의 거리 구하기

먼저 인접한 좌표점 사이의 지상거리를 계산합니다.

```java
public final class GeoDistance {

    private static final double EARTH_RADIUS_M = 6_371_000.0;

    private GeoDistance() {}

    public static double haversine(
        double lat1,
        double lon1,
        double lat2,
        double lon2
    ) {
        double phi1 = Math.toRadians(lat1);
        double phi2 = Math.toRadians(lat2);
        double deltaPhi = Math.toRadians(lat2 - lat1);
        double deltaLambda = Math.toRadians(lon2 - lon1);

        double a = Math.sin(deltaPhi / 2) * Math.sin(deltaPhi / 2)
            + Math.cos(phi1) * Math.cos(phi2)
            * Math.sin(deltaLambda / 2) * Math.sin(deltaLambda / 2);

        return 2 * EARTH_RADIUS_M * Math.asin(Math.sqrt(a));
    }
}
```

Haversine은 두 위경도 사이의 측지 직선거리를 계산합니다. 인접한 점의 거리를 합치면 지도상의 폴리라인 경로 길이를 얻을 수 있습니다.

### 5.2 경로 길이 비율로 거리 배분하기

선형 자산의 실제 길이는 두 지점의 직선거리보다 짧을 수 없습니다. 경로가 휘거나 여유 구간이 있으면 실제 길이가 더 길어집니다.

기준점 A와 B의 값이 다음과 같다고 하겠습니다.

```text
A.distance = 1,000m
B.distance = 1,600m

A에서 B까지 지도 경로 길이 = 500m
```

경로점 X가 A에서 지도 경로의 40% 지점에 있다면 거리도 같은 비율로 배분합니다.

```text
X.distance = 1,000 + (1,600 - 1,000) × 0.4
           = 1,240m
```

일반적인 계산식은 다음과 같습니다.

```text
pathRatio = A에서 X까지의 폴리라인 길이 / A에서 B까지의 폴리라인 길이
distanceX = A.distance + (B.distance - A.distance) × pathRatio
```

여기에는 하나의 가정이 들어갑니다.

> 기준점 사이에서 선형 자산의 실제 길이와 지도 경로 길이의 비율은 일정하다.

이 가정이 맞지 않을 수 있는 구간은 더 많은 기준점을 추가해 구간을 나누면 됩니다. 양 끝 기준점 바깥의 값은 기준이 없으므로 자동 외삽하지 않는 편이 안전합니다.

### 5.3 재계산 의사 코드

```java
void recalculateDerivedDistances(List<ReferencePoint> points) {
    List<Integer> anchors = new ArrayList<>();

    for (int i = 0; i < points.size(); i++) {
        if (isMeasuredDistance(points.get(i))) {
            anchors.add(i);
        }
    }

    for (int pair = 0; pair < anchors.size() - 1; pair++) {
        int start = anchors.get(pair);
        int end = anchors.get(pair + 1);

        double pathTotal = pathLength(points, start, end);
        if (pathTotal <= 0) {
            continue;
        }

        double startDistance = points.get(start).distanceM();
        double distanceSpan = points.get(end).distanceM() - startDistance;
        double pathSoFar = 0;

        for (int i = start + 1; i < end; i++) {
            pathSoFar += segmentLength(points.get(i - 1), points.get(i));
            double ratio = pathSoFar / pathTotal;
            double derivedDistance = startDistance + distanceSpan * ratio;

            updateDerivedDistance(
                points.get(i),
                roundToTenth(derivedDistance)
            );
        }
    }
}
```

재계산 대상은 측정값이 아니라 계산값입니다. 사람이 확정한 기준점까지 덮어쓰지 않으려면 distance_source를 확인해야 합니다.

## 6. 성능: 단건 조회와 일괄 조회를 나누기

이벤트 하나를 처리할 때는 다음 기준점이 필요할 수 있습니다.

- 앞쪽 좌표점
- 뒤쪽 좌표점
- 가장 가까운 설명용 점
- 가장 가까운 시설 또는 구조물 점

이벤트가 여러 개라면 이벤트마다 기준점을 질의하는 방식은 비효율적입니다.

```text
이벤트 N개 × 기준점 질의 여러 번
```

대신 경로별 기준정보를 한 번 읽고 메모리에서 반복 계산합니다.

```java
public final class PositionResolver {

    private final ReferencePointRepository repository;

    public EventPosition resolveOne(String routeId, double distanceM) {
        return EventPosition.from(
            repository.findPrevious(routeId, distanceM),
            repository.findNext(routeId, distanceM),
            repository.findNearestDescription(routeId, distanceM),
            distanceM
        );
    }

    public RoutePositionIndex loadIndex(String routeId) {
        return new RoutePositionIndex(repository.findAll(routeId));
    }
}
```

호출부는 이벤트를 경로별로 묶습니다.

```java
Map<String, List<SensorEvent>> eventsByRoute = events.stream()
    .filter(event -> event.distanceM() >= 0)
    .collect(Collectors.groupingBy(SensorEvent::routeId));

eventsByRoute.forEach((routeId, routeEvents) -> {
    RoutePositionIndex index = resolver.loadIndex(routeId);

    for (SensorEvent event : routeEvents) {
        eventPositions.put(
            event.id(),
            index.resolve(event.distanceM())
        );
    }
});
```

### 6.1 SQL과 메모리 계산 결과를 같게 유지하기

단건 경로는 SQL의 ORDER BY로 가장 가까운 점을 선택할 수 있습니다.

```sql
SELECT *
FROM route_reference_point
WHERE route_id = :routeId
  AND description IS NOT NULL
ORDER BY
    ABS(distance_m - :distanceM),
    distance_m,
    id
LIMIT 1;
```

메모리 경로도 같은 우선순위를 따라야 합니다.

```java
ReferencePoint nearest(double distanceM) {
    ReferencePoint best = null;
    double bestGap = Double.MAX_VALUE;

    for (ReferencePoint point : points) {
        double gap = Math.abs(point.distanceM() - distanceM);

        if (gap < bestGap) {
            best = point;
            bestGap = gap;
        }
    }

    return best;
}
```

SQL은 거리 차이, 거리값, ID 순으로 정렬합니다. Java는 정렬된 목록을 앞에서부터 훑으며 `gap < bestGap`일 때만 교체합니다. `<=`를 쓰면 같은 거리에서 뒤쪽 점을 선택하게 되어 SQL과 결과가 달라질 수 있습니다.

두 경로가 같은 테스트 데이터를 사용해 같은 결과를 내는지 테스트합니다.

```java
@Test
void indexAndQueryChooseTheSamePosition() {
    EventPosition fromQuery =
        queryResolver.resolveOne("route-a", 150.0);

    EventPosition fromIndex = indexResolver
        .loadIndex("route-a")
        .resolve(150.0);

    assertThat(fromIndex).isEqualTo(fromQuery);
}
```

성능을 개선하면서 계산 경로를 복제했다면, 두 경로의 등가성을 테스트해야 합니다.

## 7. 검증: 경로의 품질을 숫자로 확인하기

정답 좌표를 모든 구간에서 직접 측량할 수 없다면 독립적인 두 값을 비교할 수 있습니다.

- 기준점 사이의 측정 거리 차이
- 지도 좌표를 연결한 폴리라인 길이

두 값의 비율을 계산합니다.

```text
비율 = 측정 거리 차이 / 폴리라인 경로 길이
```

선형 자산은 경로의 굴곡과 여유 구간 때문에 지도 경로보다 길거나 같은 것이 일반적입니다. 따라서 비율이 1보다 조금 큰 범위에 모이는지 확인할 수 있습니다.

예시:

| 구간  | 폴리라인 길이 | 측정 거리 |  비율 |
| ----- | ------------: | --------: | ----: |
| A → B |          500m |      510m | 1.020 |
| B → C |          760m |      755m | 0.993 |
| C → D |          640m |      665m | 1.039 |

이 지표는 절대 정확도를 증명하지 않습니다. 대신 다음 판단에 도움을 줍니다.

- 어떤 구간의 경로 형상이 부족한가
- 기준점을 어디에 추가해야 하는가
- 추가 작업을 언제 멈출 수 있는가

직선거리를 비교 기준으로 쓰면 안 됩니다. 경로가 도로, 통로 또는 선형 자산을 따라 휘어지기 때문입니다. 비교해야 할 값은 두 기준점 사이를 실제 경로에 따라 연결한 폴리라인 길이입니다.

## 8. 물리 제약과 입력 검증

수치 검증만으로는 부족합니다. 도메인에 존재하는 물리 제약을 코드로 옮기면 잘못된 입력을 더 일찍 찾을 수 있습니다.

선형 자산의 실제 길이는 두 위치 사이의 직선거리보다 짧을 수 없습니다.

Optional<String> validateLengthConstraint(

### 8.1 좌표가 경로의 어느 구간에 놓였는지 확인하기

거리 순서와 지도상의 위치 순서가 다르면 경로가 뒤로 꺾입니다. 새 좌표가 어느 선분에 가까운지 계산해 입력 순서를 검증할 수 있습니다.

```java
public static int findNearestSegment(
    List<GeoPoint> vertices,
    double latitude,
    double longitude
) {
    if (vertices.size() < 2) {
        return -1;
    }

    int bestIndex = 0;
    double bestOffset = Double.MAX_VALUE;

    double metersPerLon = 111_320.0
        * Math.cos(Math.toRadians(latitude));
    double metersPerLat = 110_540.0;

    for (int i = 0; i < vertices.size() - 1; i++) {
        GeoPoint from = vertices.get(i);
        GeoPoint to = vertices.get(i + 1);

        double ax = (from.longitude() - longitude) * metersPerLon;
        double ay = (from.latitude() - latitude) * metersPerLat;
        double bx = (to.longitude() - longitude) * metersPerLon;
        double by = (to.latitude() - latitude) * metersPerLat;

        double vx = bx - ax;
        double vy = by - ay;
        double lengthSquared = vx * vx + vy * vy;

        double t = lengthSquared == 0
            ? 0
            : Math.max(
                0,
                Math.min(1, -(ax * vx + ay * vy) / lengthSquared)
            );

        double offset = Math.hypot(ax + t * vx, ay + t * vy);
        if (offset < bestOffset) {
            bestOffset = offset;
            bestIndex = i;
        }
    }

    return bestIndex;
}
```

이 계산은 위도에 따른 경도 축척을 보정한 뒤 점을 각 선분에 투영합니다. t를 0과 1 사이로 제한해야 선분의 연장선이 아니라 실제 선분과의 거리를 구할 수 있습니다.

### 8.2 400과 409를 구분하기

모든 경고를 저장 거부로 처리하면 사용자가 정상적인 근사값도 입력할 수 없습니다. 오류의 성격에 따라 응답을 구분합니다.

| 상태 코드 | 의미                              | 예                                      |
| --------- | --------------------------------- | --------------------------------------- |
| 400       | 입력을 수정해야 저장할 수 없다.   | 필수값 누락, 거리 중복, 좌표 형식 오류  |
| 409       | 저장할 수 있지만 확인이 필요하다. | 경로 순서 불일치, 물리 제약 위반 가능성 |
| 500       | 서버 내부 문제다.                 | 저장소 장애, 외부 서비스 오류           |

409 Conflict와 경고 목록을 사용하면 저장을 막지 않으면서도 사용자의 확인을 요구할 수 있습니다. 경고 문구는 내부 예외명이 아니라 사람이 판단할 수 있는 내용을 포함해야 합니다.

```text
입력한 거리 순서와 지도상의 위치 순서가 다릅니다.
저장하면 경로가 해당 지점에서 뒤로 꺾일 수 있습니다.
좌표와 거리값을 확인한 뒤 다시 저장하세요.
```

## 9. 자주 생기는 오류

### 9.1 구현한 로직을 화면이 호출하지 않는 경우

서버에 위치 계산 로직을 추가했는데 화면에 결과가 나타나지 않을 수 있습니다. 화면이 다른 조회 경로를 사용하면 새 로직은 실행되지 않습니다.

확인 순서는 간단합니다.

1. 브라우저 Network 탭에서 실제 요청 URL을 확인한다.
2. 서버 로그에서 해당 요청이 들어오는지 확인한다.
3. 응답을 만드는 서비스까지 요청이 도달하는지 확인한다.
4. 같은 기능을 제공하는 오래된 경로가 남아 있는지 찾는다.

코드가 존재하는지보다 실제 요청이 그 코드에 도달하는지가 먼저입니다.

### 9.2 경로 참여 여부를 boolean으로 저장하는 경우

is_route_vertex 같은 플래그로 경로 참여 여부를 저장하면 좌표와 플래그가 어긋날 수 있습니다.

```sql
-- 위험한 방식
WHERE has_coordinates = TRUE
  AND is_route_vertex = TRUE
```

좌표가 있는데 플래그가 FALSE면 경로에서 빠집니다. 경로 계산과 이벤트 보간이 서로 다른 점 목록을 사용하는 문제도 생깁니다.

경로 참여가 “좌표가 존재하는가”로 결정된다면 저장 플래그를 두지 않고 조건을 하나로 만듭니다.

```sql
WHERE latitude IS NOT NULL
  AND longitude IS NOT NULL
```

저장된 상태와 좌표에서 유도되는 사실을 중복해서 관리하지 않는 편이 안전합니다.

### 9.3 반올림과 UNIQUE 제약이 충돌하는 경우

계산 결과를 일정 단위로 반올림하면 서로 다른 두 값이 같은 값이 될 수 있습니다.

```text
12.04m → 12.0m
12.05m → 12.1m
```

반올림 결과가 기준점의 거리와 같아지면 (route_id, distance_m) 같은 UNIQUE 제약과 충돌할 수 있습니다. 반올림 정밀도, 임시 입력값, UNIQUE 정책을 함께 설계해야 합니다.

### 9.4 수정 대상 자신을 이웃으로 선택하는 경우

등록과 수정에서 같은 검증 함수를 사용하면 수정 대상 행이 자기 자신을 이웃으로 선택할 수 있습니다. 그러면 자기 자신과의 거리가 0이 되어 검증을 통과합니다.

```java
List<ReferencePoint> candidates =
    repository.findLocated(routeId).stream()
        .filter(point ->
            excludedId == null || point.id() != excludedId
        )
        .toList();
```

수정 검증에서는 대상 ID를 후보에서 제외해야 합니다.

### 9.5 사람이 확정한 값을 재계산으로 덮어쓰는 경우

자동 재계산 대상과 사람이 확정한 값을 구분하지 않으면 다음 재계산에서 수동 수정값이 사라집니다.

```java
if (point.distanceSource() == DistanceSource.DERIVED) {
    updateDerivedDistance(point);
}
```

사람이 값을 수정하는 순간 출처를 MEASURED 또는 MANUAL로 바꾸고, 재계산 로직은 그 값을 건너뛰어야 합니다.

### 9.6 변경이 없는데 재계산하는 경우

기준점이 실제로 변하지 않았는데 전체 경로를 재계산하면 불필요한 조회와 UPDATE가 발생합니다.

```java
boolean distanceChanged =
    Math.abs(oldDistance - newDistance) >= 0.05;
boolean hasCoordinates =
    latitude != null && longitude != null;

if (distanceChanged && hasCoordinates) {
    recalculateDerivedDistances(routeId);
}
```

변경 판단의 문턱은 재계산 내부의 문턱과 같아야 합니다. 두 값이 다르면 재계산을 시작하고도 실제 변경은 하지 않는 공회전이 생깁니다.

## 10. 설계 원칙으로 정리하기

### 원본과 파생값을 분리한다

센서가 준 거리는 원본입니다. 지도 좌표는 기준정보에 따라 바뀔 수 있는 계산 결과입니다. 바뀔 수 있는 값을 원본처럼 저장하지 않으면 기준정보 개선을 과거 데이터에도 적용할 수 있습니다.

### 거리와 좌표를 독립적으로 평가한다

한 점의 거리와 좌표가 항상 같은 출처에서 오지는 않습니다. distance_source와 coordinate_source를 나누면 각 값의 신뢰도를 따로 판단할 수 있습니다.

### 굴곡이 오차를 만든다

직선 구간에서는 기준점 간격이 넓어도 보간 오차가 작습니다. 경로가 꺾이는 지점에 좌표를 추가하면 같은 수의 점으로 더 정확한 결과를 얻을 수 있습니다.

### 계산 경로가 두 개면 등가성을 테스트한다

단건 SQL과 다건 메모리 색인을 함께 사용하면 성능은 좋아지지만 규칙이 복제됩니다. 같은 입력에 같은 결과를 내는지 테스트가 필요합니다.

### 도메인의 제약을 검증 규칙으로 바꾼다

일반적인 null 검사와 길이 검사는 데이터 형식만 확인합니다. 선형 자산의 길이 관계나 좌표 순서처럼 도메인에만 있는 제약을 추가하면 잘못된 입력을 더 정확하게 찾을 수 있습니다.

| ----------------------------- | -------------------------------------------------------- |
| 센서가 1차원 거리만 보낸다    | 거리와 좌표 기준점을 연결하는 선형참조 모델을 사용한다.  |
| 기준정보가 바뀔 수 있다       | 이벤트에는 원본 거리만 저장하고 좌표는 조회 시 계산한다. |

| 굴곡점의 거리를 모른다        | 기준점 사이의 폴리라인 경로 비율로 계산한다.             |
| 여러 이벤트를 처리한다        | 경로별 기준정보를 한 번 읽고 메모리에서 반복 계산한다.   |
| 계산 결과를 검증하기 어렵다   | 측정 거리와 폴리라인 길이의 비율을 비교한다.             |

| 자동 계산이 수동값을 덮어쓴다 | 값의 출처를 저장하고 계산 대상만 갱신한다.               |

1차원 거리를 지도 좌표로 바꾸는 일은 보간식 하나로 끝나지 않습니다. 원본과 파생값의 경계, 기준점의 품질, 경로의 굴곡, 계산 비용, 입력 검증을 함께 설계해야 합니다.

다음 글에서는 이 좌표를 지도 이미지로 렌더링할 때 필요한 좌표계와 타일 계산을 일반적인 서버 렌더링 관점에서 다룹니다.
